## Reading status and connections

`implemented` means the explicitly described code exists and its references were inspected. It does not mean the entire platform journey, physical-device matrix, security acceptance, deployment or store release is complete. `partial` identifies an existing foundation with missing work; `planned` identifies requirements without delivered runtime behavior. `deprecated`, `removed` and `unknown` are reserved for evidence-supported future updates.

A `depends on / reuses` edge means that the feature composes, reads or enforces another capability; `used by` is its reciprocal. These can include UI composition, persisted model relationships and SQL lifecycle hooks, not only JavaScript imports. Planned edges remain planned. Source references on both entries explain the boundary; Graphify inferred/undirected call edges cannot establish direction.

## Starting points and reuse

- Identity or revoked access: start with AUTH/SESSION and the relevant NATIVE_AUTH or WEB_AUTH entry. Membership and account access remain server-authoritative.
- Financial calculations: reuse CONTRACTS and MONEY, then the owning account/activity/report/wealth/goal service. Native screens must consume existing API/domain behavior rather than reproduce it.
- Updates and background work: start with EVENTS/JOBS. Existing web job-status subscriptions are not a completed native general-finance stream.
- Privacy, retained history or recovery: follow PRIVACY/ARCHIVE/EXPORTS/RESTORE and their actor/owner/lease boundaries before reading stored data.
- Product and delivery state: use the current [ordered plan](docs/superpowers/plans/2026-11-02-ios-only-delivery.md) and [progress record](docs/progress.md), then verify live PR/CI/merge evidence. NAV1 itself does not begin IOS3.

## Coverage and maintenance

This baseline covers every current application/package domain, shared runtime capabilities, operational tooling and the agreed future delivery families at feature level. Individual aliases, every SQL policy/version and all fixture edges are not separately enumerated. Follow linked source and the latest migrations; keep unknown details explicit. Existing web finance is retained pending native parity. No working wealth/goal UI, projection engine, paid subscription lifecycle, companion, staff analytics, statement converter or public release is implied.

The [Graphify guide](docs/features/graphify.md) records six bounded AST scopes, the local project-wide index, a feature-ID graph, excluded data and tooling gaps. Keep generated graphs local; a fresh checkout must rebuild them. Source and test paths in this tracked tree remain portable.

After changing or discovering a capability, update its entry and affected reciprocal edges in the same task. Reconcile renamed/deleted paths, statuses and consumers; refresh affected Graphify scopes at the task boundary. Verify links, symbols, source hashes and graph/tree agreement before finishing. Search the tree, graph and repository under alternate names before adding a parallel implementation; record any justified exception in the affected entry and handoff.
